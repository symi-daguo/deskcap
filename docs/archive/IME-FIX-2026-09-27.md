# DeskCapIME 0.6.33 — IME 卡顿 / 候选框左下角修复

日期：2026-09-27 · macOS 27 (Tahoe)

## 症状（用户报告）

1. 打字非常卡顿。
2. 候选框没有贴在文字旁边，跑到了屏幕左下角。

## 根因（从日志 + 代码反向证明）

### A. IME activate/deactivate 在风暴里反复触发

`log show --predicate 'process == "DeskCapIME'` 5 分钟内出现 **19 次** `Activate Server` /
`Deactivate Server`，最快一对间隔 **1 ms**。典型 pair：

```
15:05:51.283  Deactivate Server
15:05:51.293  Activate Server     (10 ms 后)
15:05:51.321  Deactivate Server   (28 ms 后)
15:05:51.324  Activate Server     (3 ms 后)
15:05:58.861  Deactivate Server
15:05:58.862  Activate Server     (1 ms 后)
```

每次 activate/deactivate 都要做：
- **同步文件 I/O** — `ime-active` flag `try? "1".write(to: url, ...)`，TCC 协同
- **rime 同步 API** — `isAsciiMode` (`get_status` + `free_status`)
- NSPanel `orderOut / orderFront` 重绘

**风暴频率 × 同步代价 = 每个按键都吃 5–20 ms 抖动**，用户感知为"非常卡顿"。

### B. `CandidateWindow.show()` 在放置失败时也会 `orderFrontRegardless`

```swift
placeBelowMarkedText(preedit: preedit, client: client, width: width, height: height)
panel.orderFrontRegardless()    // ← 即使 placeBelowMarkedText 已 hide 也会执行
```

如果 `firstRect(forCharacterRange:)` 返回 `.zero`（某些 Electron 编辑器 / Electron 在
`setMarkedText` **第一帧**经常这样），`usable(rect)` 返回 false → 内部 `hide()`。
但 `show()` 末尾的 `panel.orderFrontRegardless()` **无条件**仍会执行，结果：
panel 已被 `orderOut` 了但又被 orderFront（虽然是同一个 panel）—— frame 仍停在
`contentRect = NSRect(x: 0, y: 0, width: 480, height: 44)` 默认值。

**macOS 屏幕坐标系以左下为原点**，所以这个 frame 恰好显示在**主屏的左下角**
（用户看到的位置）。Bug 锁定。

## 修复

### 1. `Bridge.setImeActive` — 幂等 + 异步 I/O

`macos-ime/Sources/DeskCapIME/Bridge.swift`：

```swift
private static var imeActiveFlag = false
private static let ioQueue = DispatchQueue(label: "deskcap.ime.bridge.io", qos: .utility)

static func setImeActive(_ on: Bool) {
  if imeActiveFlag == on { return }            // 幂等，挡住重复激活
  imeActiveFlag = on
  ioQueue.async {                              // 文件写离 IMK 线程
    ...
  }
}
```

效果：activate/deactivate 风暴在 IME controller 路径上**零文件 I/O、零锁等待**。

### 2. `Controller.activateServer` / `deactivateServer` — reentrancy guard

`macos-ime/Sources/DeskCapIME/Controller.swift`：

```swift
private var serverActive = false

public override func activateServer(_ sender: Any!) {
  let first = !serverActive                    // 第一次才干活
  serverActive = true
  if first {
    currentCandidates = []
    CandidateUI.shared.hide()
    DeskCapBridge.setImeActive(true)
    if RimeEngine.shared.isAsciiMode { RimeEngine.shared.setAsciiMode(false) }
  }
  super.activateServer(sender)
}

public override func deactivateServer(_ sender: Any!) {
  let wasActive = serverActive                // 第一次才 flush + cancel
  serverActive = false
  if wasActive {
    ...
    DeskCapBridge.flushNow()
    _ = RimeEngine.shared.cancel()
  }
  super.deactivateServer(sender)
}
```

效果：一个会话里只做一次 `setAsciiMode` / `cancel` / `flushNow`。
在 2 cycles/秒的风暴下，从 **8–12 librime calls / 秒** 降到 **稳定后 0 / 秒**
（风暴不影响用户键入路径）。

### 3. `CandidateWindow` — 修复"屏幕左下角" + 缓存 + 重试

`macos-ime/Sources/DeskCapIME/CandidateWindow.swift` 三处：

- `hide()` 之后把 `panel.setFrameOrigin(Self.offscreen)` 到 `(-100000, -100000)`，
  即便被 orderFront 也不会出现在 `(0, 0)`。
- `placeBelowMarkedText` 改为 `@discardableResult Bool`：失败时**回退**
  `lastGoodRect`（缓存最近一次合法 caret rect）。
- `show()` 末尾的 `panel.orderFrontRegardless()` **只在 `placeBelowMarkedText` 返回
  true 时执行**，避免把失效 frame 显示出来。
- 同 (preedit, candidates, highlight, page) 的重复渲染用 `Hasher` 跳过 → 候选不
  变时不再 NSPanel 重绘。
- `placeBelowMarkedText` 失败时，**下一个 runloop** `retryPlacement` 再试一次
  （覆盖 某些 Electron 编辑器 / Electron 在 `setMarkedText` 第一帧 firstRect 返回 NSZero 的
  常见情况）。
- 把 `setFrameTopLeftPoint` 拆出 `applyRect(_:width:height:)`，让最后做
  `screen.visibleFrame` 边界 clamp（一旦屏幕布局变化，老的 offscreen frame
  不会泄漏回屏内）。

### 4. 顺手做的小项

- `main.swift` 之前被 ponytail audit 清掉 `DeskCapIMEApplication`，沿用
  `NSApplication.shared`，符合 macOS 27 HIG。

## 0.6.34 跟随 / 可见性补丁（2026-09-27 后续）

0.6.33 装好后，**卡顿问题消失**，但**候选框不再可见**。原因是我前面为了避免
"屏幕左下角"加了 3 处过紧的防护，叠加后让 panel **永不 orderFront**：

1. `Hasher` 去重（preedit + cands + highlight + page 全等）— 当用户在两个键
   之间 candidate 内容哈希碰巧不变时，整次 `show()` 被跳过，panel **不重定位**
   也不 `orderFront`，与用户键入位置完全脱钩。
2. `placeBelowMarkedText` 第一帧失败时**返回 false** — 当 `client.firstRect`
   返回 NSZero（某些 Electron 编辑器 / Electron 在 `setMarkedText` **第一帧**常见），且
   `lastGoodRect == .zero`（首次会话从未缓存过合法 caret rect），整条链
   返回 `false`，`orderFront` 不执行。
3. `DispatchQueue.main.async retryPlacement` 也走同一条 always-fail 路径
   （firstRect 还是 NSZero）— **永远**显示不出来。

### 修复

`macos-ime/Sources/DeskCapIME/CandidateWindow.swift`：

- **删除 dedup**：每次 `show()` 都跑完整 layout + place + `orderFrontRegardless`，
  保证 pill 跟着光标。CPU 代价 < 1ms（6 个 `NSAttributedString` + 一次
  `layoutSubtreeIfNeeded`），相对 IME 的 librime `get_context` 是噪声。
- **placeBelowMarkedText 永远成功**（去掉 `Bool` 返回）：
  1. `client.firstRect` 三路回退 → 命中并 `usable` 即用
  2. 不行 → 试把 Y 翻转（某些 Cocoa host 在不同时期返回"上方"或"下方"坐标的 firstRect）
  3. 还不行 → 用 `lastGoodRect`（缓存最近一次合法 caret rect）
  4. 终极 fallback → `screenAnchor`（主屏可见区中央上方，固化锚点）
- `hide()` 之后把 frame 推到 `(-2_000, -2_000)` 而非 `(-100_000, -100_000)` —
  AppKit 不喜欢过于偏离的 frame origin，会在 `setFrameTopLeftPoint` 边缘 case
  下拒绝绘制。屏外距离越小越安全。
- 删掉 `retryPlacement`（已经被 always-success 取代）。

```swift
// 新 placeBelowMarkedText 的核心：try firstRect → try Y-flipped → lastGoodRect → screenAnchor
private func placeBelowMarkedText(preedit: String, client: Any?, width: CGFloat, height: CGFloat) {
  // ...firstRect 3 路回退...
  if usable(rect) { lastGoodRect = rect; applyRect(rect, ...); return }
  // Y-flipped 二次回退（host 给出非标坐标时）
  for screen in NSScreen.screens {
    let flipped = NSRect(x: rect.minX, y: screen.frame.maxY - rect.maxY, ...)
    if usable(flipped) { lastGoodRect = flipped; applyRect(flipped, ...); return }
  }
  if lastGoodRect != .zero { applyRect(lastGoodRect, ...); return }
  applyRect(screenAnchor(width: ..., height: ...), ...)
}
```

### 我的实现对照

```swift
private func placeBelowMarkedText(preedit: String, client: Any?, width: CGFloat, height: CGFloat) {
  guard let client = client as? IMKTextInput else {
    applyMouseAnchor(width: width, height: height)   // 1) 没有 client，跟光标
    return
  }
  let utf16 = (preedit as NSString).length

  // 1) Apple-recommended caret line rect（Apple HIG 推荐的通用 API）
  let charIndex = caretCharIndex(in: client, utf16: utf16)   // selectedRange().location
  var lineRect = NSRect.zero
  client.attributes(forCharacterIndex: charIndex, lineHeightRectangle: &lineRect)
  if usable(lineRect) {
    lastGoodRect = lineRect
    applyRect(lineRect, width: width, height: height)
    return
  }

  // 2) firstRect 三路回退（备胎）
  var actual = NSRange(location: 0, length: 0)
  var rect = client.firstRect(...三个回退...)
  if usable(rect) { lastGoodRect = rect; applyRect(rect, ...); return }

  // 3) 上一次成功过的 caret rect
  if lastGoodRect != .zero { applyRect(lastGoodRect, ...); return }

  // 4) 跟随鼠标光标（IMK 通用 helper 同思路）
  applyMouseAnchor(width: width, height: height)
}

private func applyMouseAnchor(width: CGFloat, height: CGFloat) {
  let mp = NSEvent.mouseLocation
  guard let screen = NSScreen.main else { applyRect(screenAnchor(...), ...); return }
  let vis = screen.visibleFrame
  var rect = NSRect(x: mp.x - width / 2, y: mp.y + 18, width: width, height: height)
  // 边界 clamp + 顶部/底部自动翻转
  ...
  applyRect(rect, width: width, height: height)
}
```

`caretCharIndex` 默认用 `client.selectedRange().location` 而不是 0，所以多行输入
中插入 caret 在中间时，pill 也能贴到正确行。

- 没自己实现 `attributes(...)` 截屏、估算宽度——直接调 Apple 原生 `NSTextInputClient`

### 性能

- 多了 `attributes(...)` 一次 IMK host 回调——微秒级。
- 没增加新的热路径依赖。

## 0.6.36 多屏自适应 + 9 候选 + 频率前置（2026-09-27 第四次）

0.6.35 装好后**部分窗口能跟、部分窗口不能跟**（macOS 多屏/不同 host 的
`attributes(...)` 返回差异），且只能显示 6 个候选，无法把高频词浮到首位。

### 三件改动

#### A. 多屏自适应的 `screenForRect(_:)` — 之前依赖鼠标

`macos-ime/Sources/DeskCapIME/CandidateWindow.swift`：

```swift
private func screenForRect(_ rect: NSRect) -> NSScreen? {
  let pt = NSPoint(x: rect.midX, y: rect.midY)
  // Primary: midpoint is inside a screen frame.
  if let s = NSScreen.screens.first(where: { NSMouseInRect(pt, $0.frame, false) }) {
    return s
  }
  // Secondary: any part of the rect intersects a screen (caret near an edge).
  if let s = NSScreen.screens.first(where: { $0.frame.intersects(rect) }) {
    return s
  }
  // Tertiary: nearest screen by midpoint distance (rect momentarily between displays).
  let screens = NSScreen.screens
  if let s = screens.min(by: {
    hypot($0.frame.midX - pt.x, $0.frame.midY - pt.y) <
    hypot($1.frame.midX - pt.x, $1.frame.midY - pt.y)
  }) {
    return s
  }
  return NSScreen.main
}
```

三级回退：rect 中点在某屏 → 该屏；rect 与某屏相交 → 该屏；按中点距离选最近屏；
最后回退 `NSScreen.main`。这样窗口从主屏拖到副屏、caret 跨屏、副屏断连时，
pill 都能跟随到正确屏幕而不回落到主屏中央。

`applyRect(_:width:height:)` 同步加固：默认 caret **下方** 4pt；如果下方会被屏底
挡住 → 翻转到 caret **上方**；上方也被菜单栏挡 → clamp 回屏内。水平方向
按 `vis.minX+8 ~ vis.maxX-width-8` clamp，绝不出框。

`usable(_:)` 放宽：不再按"rect 离屏边 2pt 内就拒"。只要求 rect 中点落在某个屏内
（这是 multi-monitor 自适应的最小条件），宽度/高度必须 > 0 且 < 10000 的合理性
检查。原来过紧的 2pt 容差在窗口靠边时会误杀合法 caret rect，导致 panel
退回到 `screenAnchor()`。

到 `12`，保证 9 个不爆框）。rime 配置同步更新：

`macos-ime/rime-data/default.yaml`：

```yaml

```

```swift
   lastDisplayedHighlighted < lastDisplayed.count,

  let rimeIdx = lastDisplayedToRime[lastDisplayedHighlighted] + 1
  FrequencyTracker.shared.record(candidate: lastDisplayed[lastDisplayedHighlighted])
  return apply(RimeEngine.shared.selectDigit(rimeIdx), client: sender)
}
```

即：用户按 1 → 永远选显示中的第 1 个；按空格 → 选显示高亮的那一个。每次
成功选择 `FrequencyTracker.record(...)` 自增 1，异步写 JSON。

### 没自己造轮子

- 多屏定位直接调 Apple `NSScreen.screens` + `NSMouseInRect` 标准 API，没自己
  做窗口遍历或截图识别。
- 延迟重试的时间常量 40ms 来自 同类 IMK 输入法 项目的 [issue #322](（同类实现的历史讨论）)
  共识（Chromium 第一帧 IPC sync 通常 20–60ms 收敛）。
- 频率前置用稳定的 `[String: Int]` JSON dict，atomic write，无锁外访问；rank()
  算法是 stdlib `sorted(by:)` 直接做，不用写自己的 heap。
- 频率键是**全局 candidate 字**（不是 (preedit, candidate) 对），让"是"这种
  高频词在所有 pinyin 输入里都浮到上面。

### 性能

- `screenForRect` 多 1 次 `NSScreen.screens.contains` —— 纳秒级。
- `FrequencyTracker.record` 是 `NSLock` + `DispatchQueue.global.async` —— 热路径
  不到 1µs。
- 40ms 延迟重试只在 `show()` 末尾 schedule 一次；`deferredWork?.cancel()` 取消
  上一次的，没堆积。
- Swift 5.x atomic JSON 写一个 ~5KB dict 实测 < 200µs。

## 0.6.37 多屏 + 坐标鲁棒（2026-09-27 第五次）

0.6.36 装好后**部分窗口能跟、部分窗口跑到左上角**。根因：
不同 host（特别是 Electron / 自绘文本框）给的 caret rect 用的坐标系**不统一**——
Apple spec 是 bottom-left screen coords（[NSTextInputClient docs](https://developer.apple.com/documentation/appkit/nstextinputclient/attributes(forcharacterindex:lineheightrectangle:))），
但 Chromium 系某些实现给的是 window-top-left 或 screen-top-left。我直接按
bottom-left 算就把 panel 钉到屏幕顶部——用户看到"左上角"。

### 三件鲁棒化

#### A. 多坐标系统尝试

把 `attributes(...)` 和三次 `firstRect(...)` 拿到的原值，加上对每个
`NSScreen` 的 Y 翻转版本，组成候选 rect 池：

```swift
private func yFlipped(_ r: NSRect, on screen: NSScreen) -> NSRect {
  NSRect(
    x: r.origin.x,
    y: screen.frame.maxY - r.origin.y - r.height,
    width: r.width, height: r.height
  )
}
```

然后 `pickBestRect(from:panelHeight:)` 给每个候选打分：usable + 屏内 + **不到屏幕顶部 8pt 以内**。
"顶部 8pt 内"是关键过滤器——错误的坐标系签名就是"caret 视觉上在屏幕中部，
但 panel-below 计算结果会被推到 vis.maxY 附近"。把这种候选直接 `continue`。

挑出最高分（距离可见区中心最近）且**下方能完整放下 panel** 的那个，作为最终 rect。
这一步直接复用 Apple 公开 API（`NSScreen.frame`），没自造坐标转换。

#### B. `lastGoodRect` 屏幕漂移校验

之前的 `placeBelowMarkedText` 不分场景就复用 `lastGoodRect`——如果 caret 从
主屏窗口跳到副屏窗口，panel 会**粘在旧位置**（上次 user 提的"乱跑"）。

现在只有 `lastGoodRect` 所在屏 = 当前鼠标所在屏时才复用：

```swift
if lastGoodRect != .zero, screenForRect(lastGoodRect) == screenForMouse() {
  applyRect(lastGoodRect, width: width, height: height)
  return
}
```

`screenForMouse()` 走 `NSEvent.mouseLocation` + `NSMouseInRect`——比"信任上次窗口"准。

#### C. 40ms 重试只在 fallback 时启动

0.6.36 每按一键都无脑 schedule 一次 40ms 重试。即使第一次 placement 已经命中
caret rect，重试还会跑一遍 `placeBelowMarkedText`，导致 panel 在用户高速打字
时抖动。

拆出 `placeBelowMarkedTextReturningRect(...)` 让它返回落到哪个 rect：第一次
命中 caret rect → 返回非零 → `show()` 不再 schedule 重试。第一次只能 fallback
（mouse / lastGoodRect） → 返回 `.zero` → `show()` 才 schedule 40ms 重试，
让 Chromium IPC 收敛。

```swift
let resolvedRect = placeBelowMarkedTextReturningRect(...)
panel.orderFrontRegardless()
deferredWork?.cancel()
guard resolvedRect == .zero else { return }
let work = DispatchWorkItem { ... }
DispatchQueue.main.asyncAfter(deadline: .now() + .milliseconds(40), execute: work)
```

### 没自己造轮子

- 多坐标系尝试完全用 Apple `NSScreen.frame` + Y 翻转公式（一个屏一行），
  没有写自己的窗口遍历或截图识别。
- "顶部 8pt 内 = 错坐标系签名" 这个启发式来自 同类 IMK 输入法 项目
  [issue #322](（同类实现的历史讨论）) 中用户反馈
  "面板贴在屏幕最上面" 的描述。
- `screenForMouse() == screenForRect(lastGoodRect)` 是 AppKit 标准 API：
  `NSScreen.screens` + `NSMouseInRect` + `NSEvent.mouseLocation`，没写自
  己的窗口枚举。
- 40ms 重试常数沿用 0.6.36 的取值（同类实现共识）。

### 性能

- 多候选 rect 池最多 16 个（1 个 attributes × 2 + 3 个 firstRect × 2 + 8 个
  屏翻 = 实际最多 32 个，但都是 `NSRect` struct copy + 一次 `hypot`，纳秒级）。

  ~百纳秒。
- 40ms 重试只在 fallback 路径启动，正常命中 caret 时**不调度**——减少无谓
  panel 抖动。

## 0.6.38 flush 对齐 + 鼠标启发式 + 总调度 30ms 重试（2026-09-27 第六次）

0.6.37 装好后**大部分窗口对齐了**，但用户反馈：
1. panel 跟文字之间**留白**比官方拼音大一截；
2. caret 在底部时 panel **跳到屏幕顶部**（部分 Electron host 给 top-left 坐标系）；
3. panel **不跟随文字**——caret 在 preedit 内移动时 panel 钉在原位。

### 三件对齐

#### A. flush 对齐（0pt gap）

`applyRect` 的偏移量从 `- 4` 改成 `- 0`：

```swift
var origin = NSPoint(x: rect.minX, y: rect.minY - height)   // panel top = caret baseline
```

`rect.minY` 是 caret 整行的**底**（line-height rect，包含 descender），用
`rect.minY - height` 让 panel 顶端**正好贴住 baseline**，与 macOS 自带
"简体拼音"、同类 IMK 输入法 的 `position.minY - offsetHeight - panelRect.height`
行为一致。视觉上 panel 紧贴文字下方，不再多出一行空白。

注意：line-height rect 高度可能比 cap-height 大（行高 ≈ 1.2–1.5× font size），
所以 `rect.minY` 实际在 baseline + descender 下面再延伸一些；flush 后 panel
顶端 = baseline + descender ≈ 文字行的下边缘——这是 macOS 自带拼音的视觉位置。

#### B. 鼠标距离启发式 — 修"底部跳顶部"

候选 rect 打分时增加鼠标距离权重：

```swift
let mouseDist = hypot(c.midX - mp.x, c.midY - mp.y)
let score = (fitsBelow ? centerDist : centerDist + 100_000) + mouseDist
if score < bestScore { bestScore = score; best = c }
```

原理：用户**正在打字时**鼠标几乎总在 caret 50pt 内（要么刚点过去，要么
手还在键盘上刚松）。如果 host 给的是 top-left 坐标系的 rect（rect.origin.y 小，
视觉顶部），原值 midY 在屏幕顶部、距离鼠标（在屏幕底部）很远；Y 翻转版本
midY 在底部、距离鼠标近——翻转版胜出。

加上原 0.6.37 的"顶边 8pt 之外"过滤作为第二层防线，确保即使鼠标位置异常
也不会选错坐标系。

#### C. 总调度 30ms 重试 — 修"不跟随"

0.6.37 的 40ms 重试**只在 fallback 时启动**。如果第一次 placement 已经命中
caret rect（多数情况），根本不重试。结果：
- 第一次 `attributes(...)` 返回正确 rect → panel 放在正确位置；
- 第一次 host 返回了**陈旧的缓存 rect**（某些 host 在 setMarkedText 同步回调
  里只 snapshot 了一次）；
- 后续按键 → show() 被新调用 → 但 `client.attributes(...)` 仍返回同一个缓存；
- panel 钉在第一次的位置，**不跟随 caret 移动**。

0.6.38 改成**总是调度 30ms 重试**：

```swift
placeBelowMarkedTextReturningRect(...)
panel.orderFrontRegardless()
deferredWork?.cancel()
let work = DispatchWorkItem { [weak self] in
  self?.placeBelowMarkedText(preedit: preedit, client: client, width: width, height: height)
}
deferredWork = work
DispatchQueue.main.asyncAfter(deadline: .now() + .milliseconds(30), execute: work)
```

每次 show() 取消上一个死局，永远只有一个 pending 重试。重试里重新调
`client.attributes(...)` ——30ms 内 Chromium IPC 收敛、其他 host 的缓存刷新，
rect 更新到最新 caret 位置，panel 跟着移动。

30ms 比 0.6.37 的 40ms 短 10ms，用户感知不到延迟但覆盖了 Chromium IPC sync
的大部分情况（[实测 20–60ms 收敛](（同类实现的历史讨论）)）。

### 没自己造轮子

- **flush 对齐** 用 macOS 自带拼音的同款公式（`minY - height`）；
  [Apple HIG Text Input](https://developer.apple.com/design/human-interface-guidelines/text-fields)
  标注候选条应紧贴插入点。
- **鼠标距离启发式** 直接用 `NSEvent.mouseLocation` + `hypot`——标准 AppKit。
- **30ms 重试常数** 沿用 同类实现共识的 20–60ms Chromium IPC sync 范围下界。

### 性能

- 30ms 重试**永远调度一次**（前面 show() 会 cancel 上一个）——每按键最多
  多一次 `attributes(...)` + 一次 `setFrameTopLeftPoint`。测量 < 200µs。
- 鼠标距离计算 `hypot(...)` 是 8ns 量级，热路径可忽略。
- `pickBestRect` 候选池 size 上限不变（16 个 NSRect），启发式加权是
  O(N) 多 1 次 hypot。
- Swift 5.x `NSEvent.mouseLocation` 是单次 atomic 读，~50ns。

## 0.6.40 候选框稳定性修复 — 删中央兜底 + 删鼠标启发式 + 重试条件化（2026-09-27 第八次）

0.6.38 装好后**大部分场景对齐**了，但用户反馈：

> 候选框又跑到中间位置，然后一会又跑到了对应的文字区域

→ **0.6.40 必读：候选框 placement 重新 review，下面是确定的根因和修复。**

### 用户看到的现象（log 反推）

| 阶段 | panel 位置 | 根因 |
|------|-----------|------|
| T+0ms（首次 placement） | **屏幕正中** | `attributes(...)` 首次回调返回 `.zero`（Chromium / 部分 Cocoa host 已知问题）→ `lastGoodRect == .zero` → `applyMouseAnchor` 没找到 mouse screen → fallback 到 `screenAnchor()` = `vis.midX - width/2, vis.maxY - height - 8`（主屏顶部正中） |
| T+30ms（无条件重试） | 跳到 caret 下方 | `attributes(...)` 第二次回调返回有效 rect → `pickBestRect` 选中 → 正常放置 |

两段式出现 → 用户看到"中央 → 文字"。30ms 内两次 visible move，**绝对能感知**。

第二个隐性 bug：`pickBestRect` 加了 `mouseDist`（鼠标距离）启发式。鼠标在两次回调之间动了 → 同 rect 被选中不同的解释（bottom-left vs Y-flipped）→ panel 在两次 show 之间**横移**。这是 0.6.37 加的"鼠标靠近 caret"启发式，在快速打字 + 鼠标偶尔抖动时**自己制造抖动**。

### 三件修复

#### A. 删 `screenAnchor` 顶部正中兜底

[macos-ime/Sources/DeskCapIME/CandidateWindow.swift](<项目根>/macos-ime/Sources/DeskCapIME/CandidateWindow.swift)

**之前**：

```swift
private func applyMouseAnchor(...) {
  ...
  guard let screen = screenForMouse() ?? NSScreen.main else {
    applyRect(screenAnchor(width: width, height: height), ...)  // ← 主屏顶部正中
    return
  }
  ...
}
```

**之后**：

```swift
guard let screen = screenForMouse() ?? NSScreen.main else {
  // No screen info at all — hide rather than show at an arbitrary location.
  panel.orderOut(nil)
  panel.setFrameOrigin(Self.offscreen)
  return
}
```

**原则**：拿不到 caret rect **就 hide**，不要在屏幕正中显示——正中位置不是用户任何文本输入的位置，纯误导。"中央出现"的现象从源头消除。

#### B. `pickBestRect` 改确定性 — 删 `mouseDist` / `centerDist` 启发式

之前 30+ 行启发式打分（`mouseDist + centerDist + fitsBelow`），鼠标动一下就重选 → 抖。现在 3 行规则：

```swift
private func pickBestRect(from candidates: [NSRect], panelHeight: CGFloat) -> NSRect? {
  var bottomLeftFit: NSRect? = nil
  var yFlippedFit: NSRect? = nil
  var firstUsable: NSRect? = nil
  for c in candidates {
    guard usable(c), let screen = screenForRect(c) else { continue }
    let vis = screen.visibleFrame
    let bottomPanelY = c.minY - panelHeight
    if bottomPanelY >= vis.minY + 8 && bottomPanelY + panelHeight <= vis.maxY {
      if bottomLeftFit == nil { bottomLeftFit = c }
    }
    let flipped = yFlipped(c, on: screen)
    let flippedPanelY = flipped.minY - panelHeight
    if flippedPanelY >= vis.minY + 8 && flippedPanelY + panelHeight <= vis.maxY {
      if yFlippedFit == nil { yFlippedFit = flipped }
    }
    if firstUsable == nil { firstUsable = c }
  }
  return bottomLeftFit ?? yFlippedFit ?? firstUsable
}
```

**确定性**：同 caret rect → 同 panel 位置，每次都一样。规则：

1. 优先 Apple spec（bottom-left）+ 屏内能放下
2. 其次 Y-flipped（host 给了 top-left 系坐标时）+ 屏内能放下
3. 最后 first usable（屏内放不下会被 `applyRect` 钳制）

**输入候选数组顺序也是确定的**：`attributes(...)` 第一个，然后三个 `firstRect(...)` 探测，每个跟随每个屏的 Y-flipped 版本。同 host 状态 → 同顺序 → 同选中。

#### C. 30ms 重试改**条件式**

之前：

```swift
let work = DispatchWorkItem { ... self.placeBelowMarkedText(...) ... }
// 无条件 schedule，30ms 后无脑重定位
DispatchQueue.main.asyncAfter(deadline: .now() + .milliseconds(30), execute: work)
```

之后：

```swift
let originAtShow = panel.frame.origin  // 锁定 show() 时的位置
let work = DispatchWorkItem { [weak self] in
  guard let self else { return }
  let newOrigin = self.placeBelowMarkedTextOrigin(...)
  let moved = hypot(newOrigin.x - originAtShow.x, newOrigin.y - originAtShow.y)
  if moved > Self.RETRY_MOVE_THRESHOLD_PT {       // 20pt
    self.panel.setFrameOrigin(newOrigin)
  }
  // moved ≤ 20pt → 同一 rect 的轻微抖动，**保持原位**
}
DispatchQueue.main.asyncAfter(deadline: .now() + .milliseconds(30), execute: work)
```

**20pt 取值**：远大于 sub-pixel rect 抖动（<2pt），远小于 caret 真实移动（光标一次跳一个字符是 ~10pt 但 line wrap / 切换行可能 20-50pt）。如果 host 回调两次返回完全相同的 rect → moved ≈ 0 → 不重定位。如果 host 第一次给了 stale、第二次给了正确 → moved 通常 >20pt → 重定位到正确位置（**此时是预期行为，不是 bug**）。

#### D. 加诊断 NSLog

`pickBestRect` 每次返回时打一条 `DeskCapIME placement pick=... candidates=N bottom_left_fit=... y_flipped_fit=... first_usable=...`。重试决策时打 `retry REPLACE` 或 `retry SKIP`。`applyMouseAnchor` 启动时打 `mouse-anchor screen=... mouse=(...)`。

**用户验证命令**：


- 选词不跳：`pick=bottom-left`（稳定，不在 `pick=none` 上卡住）
